# LumaRPL port 19.14 — resilient Wi-Fi

Startup time sync and manual currency refresh now share a cooperative join controller. A new request gets one second of grace; failure/handshake status must then remain stable for one second before retry. Network-not-found needs five seconds. Association and DHCP waiting are allowed to continue within the 35-second join deadline. Transient authentication status alone does not establish that a password is wrong.

Each join session permits three requests. A rejected request disconnects the station, followed by 250 ms settling and 1 or 3 seconds of backoff. Only manual refresh may fully deinitialize/reinitialize the driver once, before request three. Security stays WPA2-AES (or an explicitly configured open network); no insecure fallback or TLS-check bypass is added. Manual refresh keeps its 90-second overall limit. NTP retains two servers, each with four-second DNS and reply budgets. SDK initialization itself is synchronous and cannot be interrupted while inside the SDK.

Saved credentials enable an initial quiet clock session and at most three later sessions, 30, 120 and 300 seconds after failures. The entire window is limited to ten minutes from boot; a retry that cannot begin before the cutoff is omitted. A clock session is bounded to 55 seconds. The driver remains initialized but the station is disconnected between delayed sessions, trading temporary heap/battery use for avoiding later cold-init pauses. Startup does not download currency rates or show errors. Initial driver initialization happens before calculator input; subsequent waiting is polled cooperatively.

Manual refresh has sole ownership while it runs. It invalidates pending startup DNS/UDP work. If it fails before acquiring valid time, the remaining automatic schedule may resume; a waiting retry retains its original due time. Successful time acquisition, a manual refresh using valid manual UTC, Esc during refresh, manual clock editing, Forget credentials or successfully saving changed credentials cancels automatic sync for this boot. Using different unsaved credentials for a manual refresh also retires the old snapshot. Terminal paths release the driver when no automatic retry remains. Failed downloads keep the active currency table unchanged.

Radio / connection keeps its simple status display. F1 Refresh observes it; F4 Details shows the last three join attempts, elapsed time, link status, numeric event/status/reason, pending clock retry and SDK initialization heap delta. No SSID, password or packet payload is recorded there. The heap delta measures allocations around SDK initialization/station enable, not total free heap or every possible future SDK allocation. Its value requires device observation.

## Build and host verification

The calculator arena (208 KiB), bounded heap (96 KiB), reserved stack (32 KiB), RGB332 framebuffer (100 KiB) and shared workspace (16 KiB) remain unchanged. Arm application retry/diagnostic state is bounded at 392 bytes, including the 240-byte boot client allocated from the existing heap. Static RAM rises 104 bytes versus port 19.13. Final flash consumption is 1,961,744 bytes; the unallocated internal SRAM gap is 5,568 bytes. The current linker report is authoritative; SDK retained heap is not inferred from host stubs.

Address/undefined-behavior sanitizer tests execute the production join controller and radio/background adapters with simulated SDK I/O. They cover transient/stable handshake failures, three attempts, discovery/DHCP deadlines, four delayed sessions, manual reset/ownership/resume/cancel, stale DNS, NTP packet validation, resource/allocation failures, timer wrap and cleanup. Controller tests use the production engine, fonts, RGB332 renderer and readers; radio/storage boundaries are mocked. Changed status/Details/help captures are reviewed in all eight themes. Mathematics, fonts and desktop engine source are compared with the prior source archive; the clean 8,447-test port 19.8 desktop suite is inherited, not represented as a fresh full-suite run. Loader partition, memory and stack-allocation checks accompany the release.

These checks cannot establish real access-point reliability, battery cost, runtime SDK heap usage or device responsiveness. Physical acceptance remains pending. SD deployment is a separate requested action.

## Device acceptance

1. Cold boot with saved credentials in good signal. Continue calculating while time sync proceeds silently. Confirm local date/time; startup must not refresh exchange rates.
2. Under Conversions > Currency conversion, refresh once. A temporary failure should retry automatically, with attempt counts visible. Confirm time/rates and immediate conversion; reopen Conversions and restart to check the cache.
3. Open Settings > Network > Radio / connection > F4 Details. Check attempts, link/events, retry countdown and the measured SDK heap delta. Main status must remain limited to radio/connection.
4. In weak/no signal, keep calculating. Observe delayed retries; move into coverage before ten minutes. No startup error dialog should appear. Once synchronized, no pending retry should remain.
5. Start a manual refresh during startup sync; Esc must cancel it and end automatic retries. Repeat with manual UTC, manual clock edit and Forget credentials. A failed manual refresh without cancellation/time should resume only the remaining boot schedule.
6. Check that repeated refreshes, cancellation, graphing/Lua and loader return remain usable during a 30-minute mixed-use session. Report whether the first refresh succeeds and share numeric Details if not; never share the password.
